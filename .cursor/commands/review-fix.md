# レビュー指摘の検討・対応

## 概要

PR やコードレビューで指摘された内容を受け取り、項目ごとに現行コード・既存テスト・必要最小限の確認結果を根拠として「有効 / 一部有効 / 無効」を判定する。そのうえで「修正する / 一部のみ修正する / 見送る」を決める。複数項目がある場合は 1 件ずつ確認してから結論を出す。修正が不要な項目には編集・テスト追加・ログ更新を行わない。

## 判定ルール

1. 指摘内容が複数含まれる場合、まず項目ごとに分解する
   - ファイルごと、論点ごと、提案ごとに独立した項目として扱う
   - 1つの項目を対応したからといって、他の項目を未確認のまま終了しない

2. 各項目を独立して判定する
   - 判定は必ず「有効 / 一部有効 / 無効 / 要確認」で表現し、「妥当そう」「たぶん」「seems valid」などの曖昧表現で済ませない
   - 判定は必ず現行コード・既存テスト・今回実行した確認結果のいずれかを根拠にする
   - 有効な指摘 → 修正を実施する
   - 無効な指摘 → 理由を説明して見送る
   - 判断に迷う場合 → 実装前に確認する
   - 一部有効とは、問題意識は妥当だが、指摘の範囲・原因・提案された修正の一部が現状コードやテストと一致しない場合を指す
   - 一部だけ対応し、一部を見送ることを許可する
   - 無効または対応不要の項目については、ファイル編集・テスト追加・`.cursor/review-feedback/log.md` 更新を行わない

3. 修正に入る前に、指摘内容と現状実装のズレを確認する
   - 指摘文の問題意識と、実際の欠落箇所が一致しているかを確認する
   - 指摘の提案がずれている場合は、そのまま鵜呑みにせず、本当に直すべき最小差分へ言い換えてから着手する

## 修正時の進め方

1. 最小差分で修正する
   - 既存パターンに合わせる
   - 既存の動作を壊さないことを優先する

2. 検証方法を変更内容に応じて選ぶ
   - 挙動変更、バグ修正、分岐追加 → テスト戦略ルール（`test-strategy.mdc`）に従い、テスト観点表を提示して TDD で進める
   - 軽微な文言修正、コメント修正、アクセシビリティ属性追加、表示のみの微修正 → フル TDD を必須にせず、必要十分な回帰確認を行う

3. 検証は最小スコープで実施する
   - まず関連する単体テスト、Feature テスト、または最小の確認コマンドだけを実行する
   - 必要な場合のみ確認範囲を広げる

4. 修正後の仕上げを行う
   - `vendor/bin/pint --dirty` で整形する
   - `.cursor/rules/review-feedback-prevention.mdc` の「6) 強制運用ゲート」に該当する場合、つまりコミット対象に `app/` `tests/` `database/` `routes/` `config/` `bootstrap/` `resources/` のいずれかが含まれる場合は、`.cursor/review-feedback/log.md` を更新する
   - 上記条件に該当する場合は、採用指摘がないケースでも `classification: none` として「判定した事実」を残す

## 結果報告

- 各項目ごとに次を明示する
- 判定: 有効 / 一部有効 / 無効 / 要確認
- 対応方針: 修正した / 一部のみ修正した / 見送った / 要確認
- 理由: 現行コードの根拠・既存テストの根拠・今回の確認結果のいずれかを明記する
- 実施内容
- 検証結果

## 注意

- 修正が不要なら編集しない
- 指摘文の言い回しをそのまま採用せず、必ず現状実装と突き合わせて判定する
- テストは常に変更内容に見合う最小スコープから始める
- 指摘に同意できない場合は、技術的根拠を示したうえで意見を述べる
- 複数項目を受け取った場合でも、必ず1件ずつ確認してから結論を出す
