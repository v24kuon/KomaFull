# レビュー指摘の検討・対応

## 目的（必ず守る）

指摘文は **未検証の主張** として扱う。実装・ファイル編集に着手する前に、**現行コード・ルート定義・フレームワークの挙動・テスト**のいずれかで **指摘の前提が真か** を確認する。**前提が誤り・過剰・既に解決済み**なら対応しない。**対応が必要**と判断した項目だけ最小差分で直す。

> 典型例: モデルや `routes/web.php` を変更した後も、古い指摘（「`getRouteKeyName` がない」等）がそのまま残ることがある。**指摘の文章を信じて即修正しない。**

### Git（コミット・プッシュ）

**ユーザーから明示的に依頼されない限り** `git commit` と `git push` を実行しない。本コマンドの通常の完了地点は、検証・必要な修正・関連テスト・`.cursor/review-feedback/log.md` の更新（運用で求められる場合）までとする。

---

## フェーズ0: 項目の分解

1. 指摘を **独立した項目** に分割する（ファイル単位・論点単位・提案単位）。
2. 各項目に **ID** を付ける（例: R-01, R-02）。
3. 項目ごとに **後続フェーズを完走** する。1件だけ直して終了しない。

---

## フェーズ1: 対応要否の検証（必須・編集より先）

各項目について、**次を順に埋め、根拠を残してから** フェーズ2へ進む。

### 1.1 指摘の主張を一文で言い換える

- 何が **欠けている / 間違っている / 危険** だと言っているか（実装者向けの技術主張に落とす）。

### 1.2 現状との突合（ツールで確認）

次のうち **該当するものを必ず実行** し、指摘と矛盾しないか確認する。

| 確認対象 | 例 |
|----------|-----|
| 該当ファイルの **現在の内容** | `Read` / `Grep` / シンボル検索 |
| **ルート・バインディング** | `routes/web.php`、`php artisan route:list`、ルートパラメータ `{model:column}` の有無 |
| **モデル** | 該当モデルの `getRouteKeyName`、リレーション、制約 |
| **既存テスト** | 関連 Feature テストが既にカバーしていないか |
| **フレームワーク仕様** | Laravel のルートモデルバインディング・`route()` 生成の仕様（必要なら **search-docs** / 公式ドキュメント） |

**禁止**: 指摘文だけを根拠に「対応が必要」と結論を書くこと。

### 1.3 判定（項目ごとに必ず1つ）

| 判定 | 意味 | 次のアクション |
|------|------|----------------|
| **対応不要** | 前提が誤り、または既に満たしている、または指摘の範囲が過剰 | ファイルを編集しない。報告で根拠を述べる |
| **一部対応** | 問題意識は妥当だが、提案コードや対象ファイルがズレている | ズレを言い換えたうえで **最小差分** のみ |
| **対応必要** | 現状コード・挙動・セキュリティ上、修正が妥当 | フェーズ2へ |
| **要確認** | 情報不足、本番データ依存、プロダクト判断が必要 | `AskQuestion` またはユーザーへ確認。**推測で実装しない** |

### 1.4 「モデル・ルートを変えた後」の指摘への注意

次を疑う:

- 指摘が **マージ前の差分** 前提になっていないか。
- **`{resource:column}`** 等、ルート側でキー列が明示されていないか（その場合、レビュアの「デフォルトは id」の主張が **URL 生成** にだけ当てはまる等、整理が必要）。

---

## フェーズ1.5: サブエージェント（Task）の利用

**全件に Task を使う必要はない。** 次のとき **Task**（`subagent_type` は用途に応じて `code-reviewer` / `verifier` / `generalPurpose` 等）で **追加検証** し、その **出力を根拠に判定** する。

- 指摘が **セキュリティ・認可・トランザクション・並行** に触れる。
- **アーキテクチャ・大きな副作用**（公開 URL と管理 URL のルートキー統一など）が絡む。
- 自分の読みだけでは **Laravel の挙動に自信が持てない**（ルートバインディング・`route()` のキー解決など）。

**ワークスペースルール**: 代筆禁止。Task の戻り値をそのまま根拠にし、**存在しないサブエージェント実行を装わない**。

---

## フェーズ2: 修正の実施（対応必要・一部対応のみ）

1. **最小差分**・既存パターンに合わせる。
2. 挙動・分岐が増える変更は `.cursor/rules/test-strategy.mdc` に従い、観点とテストを検討する。
3. 軽微な修正は最小の回帰確認でよい。
4. 整形: `vendor/bin/pint --dirty`（対象ファイルに合わせる）。
5. `.cursor/rules/review-feedback-prevention.mdc` のゲート: コミット対象に `app/` `tests/` `database/` `routes/` `config/` `bootstrap/` `resources/` が含まれる場合は **`.cursor/review-feedback/log.md` を同一意図で更新**（採用なしでも `classification: none` で判定事実を残せる運用のときはそれに従う）。

**対応不要の項目では** ファイル編集・テスト追加・ログ更新を **しない**（運用で必須とされるログのみ例外ならルールに従う）。

---

## フェーズ3: 結果報告（項目ごと）

各項目について、次を **箇条書きで** 書く（曖昧語禁止）。

1. **判定**: 対応不要 / 一部対応 / 対応必要 / 要確認（従来の「有効・無効」に相当するが **「修正したか」** と混同しない）。
2. **対応方針**: 修正した / 一部のみ修正した / 見送った / ユーザー確認待ち。
3. **指摘の前提が正しかったか**: はい / いいえ / 一部（**根拠**: ファイル行・テスト名・コマンド結果・ドキュメント要約）。
4. **実施内容**（見送りなら「編集なし」と明示）。
5. **検証**: 実行したテスト・コマンド。

## チェックリスト（自己検証用）

- [ ] 指摘を項目に分割し、**少なくとも1項目は** 現行コードまたはルート定義を読んだか。
- [ ] 「対応必要」と書く項目すべてに、**具体的な根拠**（パス・行・挙動）があるか。
- [ ] **対応不要**で終わる項目に、手を入れていないか。
- [ ] サブエージェントを使った場合、**捏造ではなく実際の Task 結果**に基づいているか。

---

## 注意（短く）

- 指摘の **言い回しをそのまま実装にしない**。本当に直すべき差分に言い換えてから着手。
- 複数項目は **1件ずつ** フェーズ1→2→3 を繰り返す。
- ユーザーが「直して」と言っていても、**前提が誤りなら** 修正せず、根拠付きで説明する（ルールと矛盾する場合はルールに従う）。
- **コミット・プッシュは、ユーザーから明示しない限り行わない**（上記「Git（コミット・プッシュ）」参照）。
